## 1. Context & Problem Statement

We need to design and specify a Java 21 console application for a **Falling Bricks Game** in the `java-test` repository.
In this game:
- Players control falling **bricks**, each composed of **three blocks**, where each block is marked with a printable 7-bit ASCII symbol (`0x21..0x7E`, e.g., `@`, `#`, `$`, `%`, `&`).
- Bricks can be **`HORIZONTAL`** ($1 \times 3$) or **`VERTICAL`** ($3 \times 1$) and spawn at a pseudo-random column on the top row of the grid (`Random(seed)`), dropping down 1 row on a configurable timer (`Command.TICK`) or immediately on player drop (`Command.DROP`), while supporting lateral move, toggle orientation, and cycle block order commands.
- While airborne/falling, **all bricks behave as rigid 3-block bars**. Once a brick lands, its 3 blocks lock into the grid as **independent stacked blocks** (the original 3-block brick shape no longer applies once stacked).
- Completing a horizontal row (or matching horizontal symbols) clears those blocks, and **all stacked blocks above drop independently per column under gravity**, triggering chain cascades.
- The goal is to place all bricks in a seeded, finite queue (validated to contain enough bricks to potentially overflow the grid) and clear as many rows/matches as possible without triggering a vertical overflow (`VERTICAL_OVERFLOW` $\rightarrow$ `GAME_OVER`). If the user retries (`RETRY`), the level restarts with the **exact same `seed`**.

### Explicit Evaluation Criteria & Architectural Advice
The design must satisfy these non-negotiable engineering constraints:
1. **Validate Everything**: Empty inputs, invalid symbols (`non-ASCII` or whitespace), invalid orientations, negative/undersized/oversized grids (`min >= largestConfiguredBrickSpan [3]`, `max` configurable default `20x20`), insufficient brick counts (must be enough to potentially cause vertical overflow), out-of-bounds lateral moves, vertical overflow on lock, and dodgy commands must all be caught and reported cleanly via structured `ValidationResult` / `ValidationErrorCode` types.
2. **Clean, Immutable Domain Model**:
   - Avoid mutable public fields on value types (use Java 21 `record`s and immutable value objects).
   - Copy collections and 2D arrays defensively (`List.copyOf(...)`, deep array cloning on snapshot boundaries).
   - **Zero hardcoded file paths** anywhere in production or test code (configuration loaded via `InputStream`/`Properties` and CLI flags; I/O via injected `Reader`/`Writer`).
3. **Test Actual State, Not Console Output**:
   - Unit tests assert directly against `GameSnapshot`, `Grid`, `Brick`, `PlacementOutcome`, and `ValidationResult` at pre-agreed test seams.
   - Include real multi-component integration tests (`FallingBricksIntegrationTest`) wiring real collaborators together without mocks.
4. **Clean Architecture, Logging & Code Hygiene**:
   - Dependency direction: `ui / cli / config` $\rightarrow$ `service / engine (ports)` $\rightarrow$ `domain` (pure Java 21, zero I/O or framework dependencies in `domain`).
   - **SLF4J + Logback Logging**: Structured diagnostics logged via SLF4J (`org.slf4j.Logger`) to `STDERR` / rolling log file so log output never corrupts the ASCII console board on `STDOUT`.
   - Consistent style, clear naming (`GLOSSARY.md`), comprehensive `README.md`, and zero dead/unused code.

## 2. High-Level Exploration of Similar Work (Arcade Falling-Block Engines)

| Classical Game / Engine | Piece Geometry | Drop & Lock Physics | Match & Gravity Resolution | Lessons Adopted for Falling Bricks |
| :--- | :--- | :--- | :--- | :--- |
| **Columns** (Sega, 1990) | 3-block vertical bar; player cycles symbol order (`[A,B,C]` $\rightarrow$ `[C,A,B]`) | Drops into column; locks on floor/stack contact | 3+ matching symbols clear; independent per-column block gravity + chain cascades | Adopted 3-block symbol cycling (`CYCLE`), post-clear **independent single-block column gravity** (`Q4`), and cascading chain multipliers. |
| **Tetris** (Pajitnov, 1984) | 4-block tetrominoes; 4 orientations | Rigid piece movement & drop; top-out overflow ends game | Full horizontal row clears; rows above shift down | Adopted **rigid-bar airborne physics** (`Q3`: a horizontal $1 \times 3$ brick stops as a rigid bar when *any* of its 3 blocks contacts floor/stack below), **horizontal full-row / row-match clears** (`Q4`), and **vertical overflow game-over** (`Q5`). |
| **Puyo Puyo / Lumines** | 2-block or $2 \times 2$ multi-symbol pieces | Timed fall + soft/hard drop; seeded PRNG queues | Post-lock splitting into individual blocks + gravity | Adopted **seeded PRNG level generation** (`Q1`: `Random(seed)`) with **same-seed level retry** (`RETRY`) and separation of **rigid airborne `Brick`** from **independent stacked `Block`s** (`Q3` + `Q4`). |

## 4. Consequences

### Positive
- **100% Deterministic & Reproducible Testing**: Because `SeededBrickGenerator` uses `Random(seed)` (`DEC-05`) and timer gravity uses `Command.TICK` (`DEC-06`), any level—including random top-row spawn positions, brick orientations, and block symbols—can be replayed deterministically in JUnit 5 tests and via the player's `RETRY` command.
- **Complete Input & State Safety**: Every boundary (CLI args, `Properties` stream, `Grid` bounds, `Brick` ASCII symbols, `brickCount` overflow capacity, player commands, lateral movement, and vertical overflow) returns a typed `ValidationResult<T>` (`DEC-03`) and logs rejections at `WARN` via SLF4J (`DEC-10`).
- **Extensible Geometry Without Overbuilding**: Encapsulating span calculations on `Brick` (`DEC-13`) and keeping `SeededBrickGenerator` behind the `BrickGenerator` interface (`DEC-12`) prepares the architecture for Future Expansion Points 1 and 2 with zero dead code today.

### Risks & Mitigations
- **Console Timer vs. Blocking Line Input**: In interactive console mode, reading commands while a timer ticks every `tickIntervalMs` requires thread-safe coordination. We mitigate this by keeping `FallingBricksEngine` single-threaded/synchronized around `execute(Command)` and having `ConsoleGameRunner` funnel both scheduled timer `TICK`s and user input lines into a single blocking command queue (`BlockingQueue<String>`). Unit and integration tests invoke `engine.execute(...)` or feed deterministic `Reader` streams directly without sleeping.
